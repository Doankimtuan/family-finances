## Measurement method

I froze the pre-experiment source and built the control before replacing the local production build. The source archive is `output/bottom-navigation-phase2/control-source.tar.gz`; its snapshot checkout was `/var/folders/tc/837jq90d23qbm4r36f_nnxkm0000gn/T/vinha-nav-phase2-control-yhjyj4tj`. The archive excludes secrets, dependencies, build output and Git metadata. Both builds used the same local production environment. The experimental source was restored to the frozen Money page and loading boundary after measurement; no Phase 2 production code remains changed.

Control and candidate ran through `bun run build` and `bun run start` on the same local production port, with the already-connected Brave browser, authenticated account, hosted backend and Vietnamese locale. Valid matched windows were interleaved Control B → Candidate B → Control C → Candidate C. For each measured transition, B and C contribute five warm cycles each (n=10); each block also had an uncounted warm-up cycle. The comparison used a 440 × 900 viewport. The earlier candidate A window used a mismatched viewport and is excluded.

Markers came from actual route DOM and rendered-frame observations, plus CDP request records; no fixed sleep was used to declare content ready. Tap feedback is the first sampled frame showing the requested tab state. Destination shell is the committed destination with its page shell rendered. Useful and primary milestones are the route-specific content above. Skeleton-free means the destination's visible main content no longer contains loading skeletons. Layout stable means the observed content and navigation geometry remained unchanged over the stabilization frames. These are browser DOM timings, not hardware display or FPS measurements.

## Critical path and integrity

The main candidate was splitting Money's single page-level barrier so account rows could render before savings, investment, debt and loan modules. The current page awaits session and active-household membership, then waits for translations and `getRealPosition`, credit cards, savings summary, debts, loan summaries and investment summary in one `Promise.all`. The account row needs fewer data domains than the complete hero and module stack, so that grouping is a credible source-level blocker.

A targeted control production trace confirmed these independent reads run concurrently after authorization: ledger position about 273 ms, card reads about 396 ms, investment about 413 ms, liabilities about 420 ms, household context about 453 ms and savings summary about 475 ms. In the same trace, session lookup was about 383 ms and membership resolution about 782 ms. Spans overlap; these figures must not be summed. The gap between the fastest and slowest domain read was about 200 ms in that request, while browser first-useful medians were about 1.3 s and varied between windows. The route-level barrier is real, but a read split alone did not explain or reliably remove the full observed wait. Auth remains before the protected reads, and financial queries were not moved into the browser.

The Add Transaction page starts its account, category, jar and transaction-tag reads independently after the product session gate; the useful mode/amount marker appeared before all usable account/category controls. Plan's current-period totals and first jar row share the current plan pulse and budget path. Separating them without evidence risks showing partially available or temporally inconsistent financial context, so neither route was changed. Inbox's runtime is deliberately unmeasured and its production maintenance behavior was left intact.

No formula, period rule, query, mutation, session gate, household authorization, schema, RLS, cache, or transaction submission behavior changed. No financial data was served from a newly introduced cache. Bottom-tab link prefetch remains disabled globally; no Inbox prefetch was introduced.

RSC windows for Control C and Candidate C each contained 20 successful destination requests for 20 measured tab taps, with no prefetch request. Candidate B's captured cursor included its warm-up and recorded two speculative prefetches for the same Money account-detail route; that pair did not recur in Candidate C. Since Candidate B's window included the warm-up and the anomaly was not reproducible in the clean matched window, it does not establish a measured duplicate-request increase, but it is a concrete reason not to retain or expand speculative prefetch without further isolation. Phase 1's stable bottom navigation remained connected in the measured cycles; sampled footer/FAB vertical movement was 0 px.

## Decision and validation

The trial did not meet the Phase 2 acceptance bar: useful primary content did not arrive earlier on the measured slow Money transition with enough consistency to distinguish a code effect from backend/window variance. Candidate source passed a local production build, `bun run lint`, `bun run typecheck`, focused tests (50 passed across six files), and changed-file formatting. The frozen control also built successfully. Afterward, the Money page and loading boundary were compared byte-for-byte with the frozen snapshot, and the experiment-only component and test were removed. The existing Phase 1 production changes and unrelated dirty work were preserved.

Inbox was source-only. Reverse-direction percentiles, other locales, 390 / 768 / 1280 px, theme and reduced-motion matrices were not collected for this content experiment; no Phase 2 UI change was retained. Phase 1's navigation/back-forward and responsive checks remain the evidence for the unchanged navigation layer, not a new Phase 2 verification.

Skipped: Inbox runtime and broad responsive/theme/reduced-motion retesting, because the experiment was reverted and Inbox production can schedule maintenance. Risk: backend timing varied between interleaved windows; the candidate B log also contained a non-reproduced speculative account-detail prefetch pair.

**BOTTOM NAVIGATION PHASE 2 NO-GO — NO SAFE MEASURABLE IMPROVEMENT**
